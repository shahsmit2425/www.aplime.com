## Photo privacy, request load, abuse limits, caching and account deletion/export - October 14, 2026

**Uploads.** Every project and business photo upload is decoded and re-encoded with sharp before it reaches R2, which removes EXIF/GPS, XMP and IPTC metadata, bakes in orientation and caps the longest edge at 2560 px. The declared type must match the decoded format, and re-encoded output must still fit the 10 MB limit. The legacy presigned project-upload routes and the business-image "direct" transport were removed so no path bypasses this step; the API-proxied `PUT .../content` routes remain. Images uploaded before this release keep their original metadata until replaced (no backfill has been run). Tests use real generated JPEG/PNG/WebP fixtures; live R2 storage was not exercised.

**Load.** The workspace polls every 60 s while the notification stream is connected (10 s otherwise) and throttles focus refreshes. Verified Firebase tokens are cached for up to 30 s (never beyond token expiry, never for tokens carrying the `admin` claim), so a revoked non-admin session can remain valid for up to 30 s per API instance. Public profile lists are memoised for 30 s per API instance and sent with `max-age=15, stale-while-revalidate=30`. Public business-image redirects are cacheable for 120 s (signed URLs last 600 s), so an unlisted or deleted image can remain visible for up to two minutes in browser/CDN caches. `/api/business-images/*` has its own 1200/min rate limit; other API routes keep 240/min. API and customer web responses use gzip/brotli compression (the notification stream is excluded) and hashed `/assets/*` files are `immutable` for a year. Compression, cache headers and the SSE exclusion are not covered by automated tests and were not checked behind Render's proxy.

**Abuse limits.** Per account: 10 new projects/day, 20 messages/minute and 500/day, 5 support requests/day, 30 support replies/hour (administrators exempt from support limits), plus 5 data exports/hour. These are database-count limits and approximate under concurrent requests.

**Account deletion and export.** Settings now offers a JSON download (`GET /api/account/export`) and permanent deletion (`POST /api/account/delete`). Both require a Firebase sign-in within the last five minutes (the client re-authenticates first). Deletion is refused while the user has booked, in-progress, paused or disputed projects, is a professional assigned to any unfinished project, or has a paid membership that is not set to cancel at period end. Otherwise it cancels the customer's open requests (notifying professionals who quoted), withdraws pending estimates, deletes uploaded files and business images (R2 deletion is best effort and failures are logged), notifications, queued email, saved/blocked lists and drafts, anonymises the account row (name "Deleted user", placeholder email, `deleted_at` set by forward-only migration 019) and professional profile (unlisted), then deletes the Firebase user. If Firebase deletion fails, a later sign-in attempt is rejected and retries it. Retained by design: shared project, estimate, payment, support, audit and message records needed by other participants or for disputes, and Stripe's own customer/account records. Tests cover export scoping, active-work refusal, anonymisation, profile unlisting and the recent-sign-in check against PGlite; Firebase user deletion, Stripe, R2 cleanup, native-app file download and provider re-authentication popups were not exercised.
